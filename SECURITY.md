# Security

## Reporting a vulnerability

Email **info@iamcarla.it** with "security" in the subject. Please include steps to reproduce and do not test against accounts that are not yours. We acknowledge reports within three working days and keep you informed until the issue is closed. Please do not open a public issue for security reports.

## Authentication model

- **OAuth 2.1** at `https://iamcarla.it` (authorization server and resource server are the same origin). Discovery per RFC 8414 and RFC 9728; a `401` from `/mcp` carries `WWW-Authenticate: Bearer resource_metadata=…`.
- **Public clients only**, registered dynamically (RFC 7591). Redirect URIs must be `https://`, loopback `http://`, or a private-use app scheme; exact match at authorization time. There are no client secrets to leak.
- **PKCE S256 is mandatory**; `plain` is rejected. The `resource` parameter (RFC 8707) is checked at both endpoints so a token is bound to `https://iamcarla.it/mcp`.
- **Authorization codes** are single use (10 minutes, hash stored). Reusing a code revokes the grant it produced.
- **Access tokens** last 1 hour. **Refresh tokens** last 30 days and rotate on every use; presenting a rotated-out refresh token revokes the whole grant (theft detection). Tokens are stored hashed (SHA-256).
- **Consent is the owner's only**: staff accounts and staff sessions impersonating a customer are refused on the consent page.
- **Pairing code**: the consent page requires a single-use code generated by the customer's account manager (15 minutes, HMAC-stored, bound to that customer, five wrong attempts burn it). Without it no authorization code is issued. This is the mitigation for consent phishing through open dynamic client registration: an attacker can register an app named like a known client, but the owner has no code to type. The consent page also displays the redirect host.
- **Staff ceiling**: the account manager sets, per customer, whether the connector is enabled and the highest permission level; it is re-checked on every call, so lowering it or switching the connector off takes effect immediately for existing tokens.

## Authorization model

- Every call runs through the same tool policy as IamCarla's in-app assistant: module gating, JSON-schema validation of arguments, and a confirmation tier per tool (`none`, `auto_undo`, `confirm`, `confirm_typed`).
- `confirm` actions become pending actions that only the owner can approve in IamCarla. `confirm_typed` actions (deletes, bulk sends, publish-now) additionally require the owner to type a phrase and can never be approved through the connector, whatever the token's scopes.
- A connector token can only cancel or approve pending actions it created itself, never the owner's own. Self-approval requires a scope that is never granted through OAuth.
- Agency-staff tools require both a staff-class token and the matching real role of the account; a client token cannot reach them even with a forged scope.
- **Tenant isolation**: every query is bound to the authenticated owner's account; identifiers from another account resolve to "not found".

## Abuse controls

- 120 requests per minute per token (separate buckets per token, so one agent cannot starve another).
- At most 30 queued confirmations per hour per agent, to keep the owner's approval inbox usable.
- Idempotency keys on write tools (24 hours) so client retries do not duplicate actions.
- Rate limits on client registration and on the token endpoint.

## Data handling

- Tool results containing customer-written text (messages, leads, notes) or fetched web content are flagged `untrusted: true`; agents must treat that text as data.
- Every connector call is written to the account's audit log with the agent's name, the tool and a truncated summary; token issuance, revocation and pairing-code events are in the agency audit log.
- No credentials are ever returned after creation: tokens and pairing codes are shown once and stored hashed.
